# 技术方案：pywebview 桌面应用架构

## 1. 核心思路

项目采用“前端造壳，后端铸魂”的架构：

- 前端使用 HTML/CSS/JavaScript 绘制现代化桌面 UI。
- `pywebview` 使用系统 WebView 创建独立应用窗口。
- Python 后端负责摄像头、OpenCV、录像、文件、SQLite 和系统播放器调用。

这个方案避免传统 Tkinter 界面的粗糙感，也避免纯浏览器 Web UI 的临时感，同时比 Electron 更轻。

## 2. 架构分层

### 2.1 前端表现层

技术：

- HTML5
- CSS3
- 原生 JavaScript

MVP 阶段暂不引入 Vue、React、Vite 或 Node 构建链。原因是当前界面规模可控，手写高质量 CSS 能获得更小的复杂度和更稳定的离线运行体验。

职责：

- 主控制台布局。
- 状态卡片。
- 布防/撤防交互。
- 事件时间线。
- 设置面板。
- 播放按钮和错误提示。

设计方向：

- 深色工作台风格。
- 信息密度适中。
- 动效克制但明确。
- 不出现浏览器地址栏、端口、网页服务感。

### 2.2 桥接与外壳层

技术：

- `pywebview`
- Windows: Edge WebView2
- macOS: WebKit
- Linux: GTK/WebKitGTK

职责：

- 创建独立桌面窗口。
- 加载本地前端资源。
- 暴露 Python 方法给 JavaScript。
- 将 UI 操作传递给后端。
- 将后端事件通知给 UI。
- 调用系统默认播放器打开录像。

注意：

- JS 暴露 API 不能直接操作后台线程内部状态。
- 后台状态更新应经过线程安全队列或受控服务层。
- 不把实时视频流作为 pywebview IPC 主路径，避免桥接层承担过高频数据传输。

### 2.3 核心后端层

技术：

- Python 3.10+
- OpenCV
- SQLite
- threading / queue
- pathlib / logging

职责：

- 摄像头采集。
- 低帧率运动检测。
- 预录制环形缓冲。
- 事件录像写入。
- 缩略图生成。
- SQLite 事件存储。
- 配置管理。
- 日志与异常恢复。

说明：

- `core/` 只关心监控和录像。
- `bridge/` 只关心 UI 与 Python 通讯。
- `storage/` 只关心数据库和事件记录。
- `ui/` 是本地静态前端资源。

## 4. 数据流

1. 用户点击“布防”。
2. JavaScript 调用 pywebview 暴露的 Python API。
3. Python 桥接层通知后端引擎进入布防态。
4. 后台线程读取摄像头并低帧率检测运动。
5. 触发后，后端合成预录制片段和触发后片段。
6. 后端保存 MP4、JPG 和 SQLite 事件记录。
7. 桥接层通知前端刷新状态和时间线。
8. 用户点击播放。
9. Python 调用系统默认播放器打开本地录像。

## 5. 第一版技术决策

- UI 使用 pywebview 桌面窗口，而不是浏览器控制台。
- 前端第一版不用 Vue，保留后续升级空间。
- 事件索引用 SQLite，不用 JSONL 作为主存储。
- Webhook 告警暂缓到 v1.1。
- 预录制默认开启，但可配置关闭。
- 视频流不实时推送到前端，只推送状态和事件。

## 6. 主要风险

- Windows 环境可能缺 WebView2 Runtime。
- 摄像头可能被其他软件占用。
- OpenCV 视频编码器在不同系统上支持程度不同。
- pywebview 的 JS/Python 桥接要注意线程安全。
- 无边框窗口需要自己实现拖拽、关闭、最小化等窗口控制。

## 7. 风险应对

- 启动时检查 WebView 和摄像头可用性。
- 录像编码优先使用常见兼容格式，失败时给出清晰错误。
- UI 与后端通过服务层交互，避免跨线程直接改状态。
- 第一版可先使用有边框窗口，视觉成熟后再切换无边框窗口。
